# Planetary Chess: A Strategic Blueprint for Desktop Transformation

## 1. Executive Summary: The Desktop-First Vision

This document outlines a comprehensive strategy for transforming the existing Planetary Chess mobile application into a robust, desktop-only game. The plan addresses the core technical challenges of this transition, including the shift from a mobile-centric UI to a desktop-native experience, the implementation of a local database for user data, and the integration of a unique quiz component. The proposed architecture is designed to be efficient, scalable, and aligned with the long-term vision of operating Planetary Chess as a micro-SaaS product on planetarychess.com.

### 1.1. Core Objective: From Mobile App to Desktop-Only Game

The primary objective is to migrate the Planetary Chess game from its current mobile-first design to a dedicated desktop application for Windows, macOS, and Linux. This involves moving beyond the constraints of a mobile browser and embracing the capabilities of a native desktop environment. The transformation will focus on creating a user experience tailored to larger screens, with a UI that leverages the additional space and input methods (mouse and keyboard) available on desktop computers. This shift is not merely a change in screen size but a fundamental re-architecture of the application's delivery and interaction model.

### 1.2. Key Differentiator: The Integrated Quiz Component

A central feature that sets Planetary Chess apart from other chess applications is its integrated quiz component. This feature, which presents players with chess puzzles to solve, must be preserved and enhanced in the desktop version. The quiz system is a core part of the game's identity and a key driver of user engagement. The technical plan must ensure that this component is seamlessly integrated into the new desktop architecture, with a polished UI and a robust system for tracking user progress and performance on the puzzles.

### 1.3. Foundational Requirements: User Accounts and Persistent Scoring

To support the micro-SaaS model and provide a personalized experience, the desktop application must include a system for user accounts and persistent scoring. Unlike the mobile version, which may have relied on more transient storage, the desktop app will require a secure, local database to store user profiles, authentication credentials, and detailed scoring data. This database will be the backbone of the user management system, enabling features such as user registration, login, and the tracking of individual progress over time, including scores from both standard games and the quiz component.

### 1.4. Target Platform: A Micro-SaaS Offering on planetarychess.com

The ultimate goal of this transformation is to position Planetary Chess as a premium desktop game available as a micro-SaaS offering on the planetarychess.com website. This business model implies a focus on a high-quality, feature-rich product that users will be willing to pay for. The technical architecture must therefore be robust, scalable, and maintainable, capable of supporting future updates and new features. The desktop application will be the primary product, and its development will be guided by the principles of creating a professional, polished, and engaging user experience that justifies its place as a standalone software product.

## 2. Recommended Technology Stack and Architecture

The transformation of Planetary Chess from a mobile-centric application to a robust, desktop-only experience necessitates a carefully selected technology stack. The chosen architecture must not only accommodate the existing quiz-based gameplay but also introduce a secure, persistent system for user accounts and scoring, which are critical for its future as a micro-SaaS product. Based on an analysis of modern development practices for desktop applications, the following stack is recommended. This combination leverages the existing React codebase while introducing powerful tools for desktop packaging, local data persistence, and scalable state management. The architecture is designed to be modular, separating concerns between the user interface, the core application logic, and the data layer, which will facilitate future development and maintenance. The selection of each component is justified by its suitability for a desktop environment, its performance characteristics, and its ability to integrate seamlessly with the other parts of the stack.

### 2.1. Frontend Framework: React with Vite

The decision to continue using React as the frontend framework is a strategic one, primarily driven by the desire to leverage the existing codebase of Planetary Chess. This approach minimizes the learning curve and development time, allowing the team to focus on the new challenges of desktop development rather than rewriting the entire UI from scratch. React's component-based architecture is particularly well-suited for a complex application like a chess game, where the board, pieces, and quiz elements can be encapsulated into reusable and manageable components. The vast ecosystem of libraries and tools surrounding React provides solutions for nearly every aspect of the application, from state management to UI styling. Furthermore, the use of Vite as the build tool offers significant advantages in terms of development speed and build performance, which are crucial for an efficient development workflow.

#### 2.1.1. Rationale: Leveraging Existing Codebase and Performance

The primary rationale for retaining React is the significant investment already made in the existing mobile application. By reusing the core React components and game logic, the development team can avoid a complete rewrite, thereby accelerating the time-to-market for the desktop version. This strategy is not only cost-effective but also reduces the risk of introducing new bugs that often accompany a full-scale migration to a new framework. React's declarative nature and its efficient virtual DOM make it an excellent choice for building dynamic and interactive user interfaces, which are essential for a real-time chess game. The framework's popularity ensures a large talent pool of developers and a wealth of community support, making it easier to find solutions to potential problems. The performance of React, especially when combined with modern state management solutions like Redux Toolkit, is more than sufficient for the demands of a desktop chess application, ensuring a smooth and responsive user experience.

#### 2.1.2. Build Tool: Vite for Fast Development and Optimized Builds

Vite is a modern frontend build tool that offers a significantly faster and more streamlined development experience compared to traditional tools like Webpack. Its key innovation is the use of native ES modules in the browser during development, which eliminates the need for a time-consuming bundling process. This results in near-instantaneous server start and Hot Module Replacement (HMR), allowing developers to see their changes reflected in the application almost immediately. This rapid feedback loop is invaluable for a project of this complexity, as it greatly enhances developer productivity and reduces the time spent waiting for builds to complete. For production builds, Vite uses Rollup, a highly efficient bundler that generates optimized, tree-shaken, and minified assets, resulting in a smaller and faster-loading application. The integration of Vite with Electron is well-supported, with templates and plugins available to simplify the setup process. The combination of Vite's speed and optimization capabilities makes it an ideal choice for building a high-performance desktop application.

### 2.2. Desktop Wrapper: Electron

To transform the React web application into a native desktop application, Electron is the recommended choice. Electron is an open-source framework that allows developers to build cross-platform desktop apps using web technologies like JavaScript, HTML, and CSS. It works by combining a Chromium-based browser engine with a Node.js runtime, effectively packaging the web application into a standalone executable that can run on Windows, macOS, and Linux. This approach provides the best of both worlds: the rich user interface capabilities of the web and the power of native desktop applications. By using Electron, the development team can create a single codebase that runs on multiple platforms, significantly reducing development and maintenance efforts compared to building separate native applications for each operating system.

#### 2.2.1. Purpose: Packaging the React App for Cross-Platform Distribution

The primary purpose of Electron in this architecture is to serve as a wrapper for the React application, enabling it to be distributed and installed as a native desktop application. Electron achieves this by creating a main process, which is a Node.js environment that manages the application's lifecycle, and one or more renderer processes, which are essentially Chromium browser windows that render the UI. The React application runs within these renderer processes, just as it would in a standard web browser. However, by running inside an Electron shell, the application gains access to native OS features that are not available in a typical web environment, such as the file system, system notifications, and native menus. This allows for the creation of a more integrated and feature-rich desktop experience. The ability to package the application for multiple platforms from a single codebase is a major advantage, as it simplifies the distribution process and ensures a consistent user experience across different operating systems.

#### 2.2.2. Key Benefit: Access to Native OS APIs and File System

A key benefit of using Electron is the ability to access native operating system APIs and the file system directly from the application. This is made possible by the Node.js runtime that is integrated into the main process of every Electron application. This access is crucial for implementing features that are essential for a desktop application, such as saving and loading game data, managing user preferences, and interacting with the local file system. In the context of Planetary Chess, this capability will be used to create and manage a local SQLite database for storing user accounts and scores. The main process can securely handle all database operations, while the renderer process (the React app) communicates with it through a well-defined and secure API. This separation of concerns ensures that the UI remains responsive and that sensitive operations, such as database writes, are handled in a controlled and secure manner. The ability to leverage the full power of Node.js opens up a wide range of possibilities for extending the application's functionality beyond what is possible in a standard web browser.

### 2.3. Local Database: SQLite

For a desktop application that requires persistent data storage without the overhead of a full-fledged client-server database, SQLite is an excellent choice. SQLite is a self-contained, serverless, transactional SQL database engine that is embedded directly into the application. It is lightweight, fast, and reliable, making it ideal for storing user data, game scores, and other application-specific information on the user's local machine. Unlike other databases that require a separate server process, SQLite stores the entire database in a single file on the local file system, which simplifies deployment and management. This approach is perfectly suited for a single-user desktop application like Planetary Chess, where the data is private to the user and does not need to be shared over a network.

#### 2.3.1. Rationale: Lightweight, Serverless, and Ideal for Desktop Apps

The rationale for choosing SQLite is based on its unique characteristics that make it a perfect fit for desktop applications. Its serverless architecture means that there is no need to install or configure a separate database server, which simplifies the installation process for the end-user and reduces the overall complexity of the application. The entire database is contained within a single file, which can be easily backed up, moved, or deleted by the user if needed. This simplicity is a major advantage for a desktop application that is intended to be a self-contained and easy-to-use product. Furthermore, SQLite is incredibly lightweight and has a small memory footprint, which ensures that it will not consume excessive system resources or impact the performance of the application. Its transactional nature guarantees data integrity, even in the event of a system crash or power failure, which is a critical requirement for any application that stores important user data.

#### 2.3.2. Integration Method: Via Inter-Process Communication (IPC)

In an Electron application, the renderer process (where the React app runs) does not have direct access to Node.js APIs for security reasons. Therefore, to interact with the SQLite database, a communication mechanism is required to bridge the gap between the renderer and the main process. This is achieved through Inter-Process Communication (IPC). The main process, which has full access to the Node.js runtime, will be responsible for all database operations, such as creating tables, inserting data, and querying for information. It will expose a set of secure API endpoints using `ipcMain.handle`, which allows it to listen for and respond to requests from the renderer process. The renderer process, in turn, will use `ipcRenderer.invoke` to send requests to the main process and receive the results. This architecture ensures that the database is accessed in a controlled and secure manner, preventing the renderer process from directly manipulating the database file and protecting the application from potential security vulnerabilities. The use of IPC provides a clean and well-defined separation of concerns, with the main process acting as a secure backend for the React frontend.

### 2.4. State Management: Redux Toolkit

As the Planetary Chess application grows in complexity, with features like user authentication, persistent scoring, and an integrated quiz system, managing the application state becomes a critical challenge. While React's built-in `useState` and `useContext` hooks are sufficient for simple state management, they can become cumbersome and lead to "prop drilling" and complex state logic in larger applications. For this reason, Redux Toolkit is recommended as the state management solution. Redux Toolkit is the official, opinionated, batteries-included toolset for efficient Redux development. It simplifies the process of setting up and using Redux by providing a set of utilities that reduce boilerplate and enforce best practices. By centralizing the application state in a single store, Redux makes it easier to manage, debug, and reason about the application's data flow.

#### 2.4.1. Purpose: Managing Complex Game, User, and Quiz State

The primary purpose of Redux Toolkit in this architecture is to provide a centralized and predictable way to manage the complex state of the application. This includes the state of the chess game itself (e.g., the current board position, move history, and game status), the user's profile and authentication status, and the state of the quiz component (e.g., the current puzzle, user attempts, and score). By consolidating this state into a single Redux store, it becomes much easier to keep the UI in sync with the underlying data. For example, when a user solves a puzzle, a Redux action can be dispatched to update the user's score in the store. This action can also trigger an IPC call to persist the new score in the SQLite database. The UI components that display the score can then automatically re-render to reflect the updated value. This unidirectional data flow, which is a core principle of Redux, makes the application more predictable and easier to debug, especially as the number of stateful components and interactions grows.

#### 2.4.2. Rationale: Scalability and Predictable State Updates

The rationale for choosing Redux Toolkit over other state management solutions is based on its scalability and the predictability it brings to state updates. As the application evolves and new features are added, the complexity of the state management logic will inevitably increase. Redux provides a robust and well-established pattern for handling this complexity, with a clear separation between actions, reducers, and the store. This structure makes it easier to organize and maintain the codebase, especially when working with a team of developers. The use of pure functions for reducers ensures that state updates are predictable and easy to test. Furthermore, Redux Toolkit includes powerful development tools, such as the Redux DevTools extension, which provides a time-traveling debugger and a detailed view of the state and actions. This makes it much easier to track down and fix bugs related to state management. While the Context API can be a viable alternative for simpler applications, Redux offers a more comprehensive and scalable solution for a complex desktop application like Planetary Chess.

## 3. Core Game Components and Libraries

The successful implementation of Planetary Chess hinges on the selection of robust and well-maintained libraries for the core game mechanics. The application requires two distinct but related components: a system for presenting and managing the chess quiz, and the main chess game logic for standard play. For each of these components, there are established open-source libraries that can be leveraged to accelerate development and ensure a high-quality user experience. These libraries provide pre-built functionality for rendering the chessboard, validating moves, managing game state, and presenting puzzles, allowing the development team to focus on the unique aspects of the application, such as the scoring system and user management. The following sections detail the recommended libraries for each component and explain how they fit into the overall architecture.

### 3.1. The Quiz (Puzzle) System

The quiz component is a key differentiator for Planetary Chess, and its implementation requires a library that can handle the rendering of chess puzzles and the tracking of user progress. The ideal library should be easy to integrate into a React application and provide a clean API for interacting with the puzzle state. It should also be customizable, allowing the development team to tailor the appearance and behavior of the puzzles to match the overall design of the application. The chosen library will be responsible for displaying the chessboard in a specific puzzle position, accepting user input for moves, and providing feedback on whether the move is correct or not.

#### 3.1.1. Recommended Library: `react-chess-puzzle`

The recommended library for implementing the quiz system is `@react-chess-tools/react-chess-puzzle` . This library is a lightweight, customizable, and purpose-built React component designed specifically for rendering and interacting with chess puzzles . It is part of the broader `react-chess-tools` suite, which is built on top of the foundational `react-chessboard` and `chess.js` libraries, ensuring seamless integration with the core game logic . The primary advantage of using `react-chess-puzzle` is that it abstracts away the complex logic of managing puzzle state, validating user moves against a solution, and providing visual feedback. This allows the development team to focus on the higher-level aspects of the quiz system, such as scoring, difficulty progression, and user interface design, rather than reinventing the wheel for the underlying chess puzzle mechanics. The library provides a set of well-defined components, including `ChessPuzzle.Root`, `ChessPuzzle.Board`, `ChessPuzzle.Reset`, and `ChessPuzzle.Hint`, which can be composed together to create a fully functional and interactive puzzle interface .

#### 3.1.2. Functionality: Rendering Puzzles, Handling User Input, and Tracking Progress

The `react-chess-puzzle` library provides a comprehensive suite of functionalities that cover all aspects of the quiz component's interactive elements. At its core, the `ChessPuzzle.Board` component is responsible for rendering the chessboard based on the initial FEN string provided in the puzzle data . This board is not just a static image; it is a fully interactive component that allows users to pick up and move pieces. The library handles the visual representation of legal moves, typically by highlighting squares, which provides immediate feedback to the user and enhances the playing experience. When a user attempts a move, the library's internal logic, powered by `chess.js`, validates the move against the predefined solution sequence. If the move is correct, the puzzle state updates to "in-progress" or "solved" if it was the final move. If the move is incorrect, the state changes to "failed," and the board can be reset to its initial position . This automated handling of user input and validation significantly simplifies the development process, as it eliminates the need to write custom event handlers and move validation logic.

Beyond basic move validation, the library offers advanced features for tracking progress and providing assistance. The `useChessPuzzleContext` hook is a powerful tool for accessing real-time information about the puzzle's state. Developers can use this hook to display contextual messages to the user, such as "Make your move to start the puzzle," "Puzzle solved! Well done!", or "Incorrect move. Try again!" . This dynamic feedback is crucial for creating an engaging and user-friendly quiz experience. The library also includes a `ChessPuzzle.Hint` component, which, when activated, visually highlights the next correct move on the board, guiding the user toward the solution . The `ChessPuzzle.Reset` component allows the user to restart the puzzle at any time. These components are highly customizable and can be shown or hidden based on the current puzzle state, allowing for the creation of a sophisticated and intuitive user interface. For example, the hint button can be configured to only appear when the puzzle is "in-progress," preventing users from getting hints before they've even made their first move . This level of control and built-in functionality makes `react-chess-puzzle` an ideal foundation for the Planetary Chess quiz system.

#### 3.1.3. Integration: Connecting Puzzle Events (`onSolve`, `onFail`) to the Scoring System

A critical aspect of the Planetary Chess quiz component is its integration with the user scoring system. The `react-chess-puzzle` library facilitates this integration through its event-driven architecture, specifically via the `onSolve` and `onFail` callback props on the `ChessPuzzle.Root` component . These callbacks are triggered at key moments in the puzzle-solving process, providing a direct hook for updating the user's score and tracking their progress. When a user successfully completes a puzzle, the `onSolve` callback is invoked, receiving the puzzle context as a parameter. This context contains valuable information, such as the number of moves it took to solve the puzzle, which can be used to calculate a more nuanced score (e.g., bonus points for solving in fewer moves). The `onFail` callback is triggered whenever the user makes an incorrect move, allowing the application to penalize the user, perhaps by deducting points from their total score . This event-based model provides a clean and decoupled way to connect the puzzle's internal state to the application's external logic.

The implementation of this integration would typically involve dispatching Redux actions within the `onSolve` and `onFail` callbacks. For example, the `onSolve` callback could dispatch an action like `puzzleSolved(puzzleId, movesPlayed)`, which would then be handled by a Redux reducer to update the user's score in the application's state. This state change would then trigger a re-render of the UI to display the updated score. Simultaneously, a side effect, such as a thunk or a saga, could be triggered to persist this new score to the local database. This would involve making an IPC call from the renderer process to the main process, instructing it to update the user's record in the SQLite database. This entire flow—from a user action in the puzzle component to a persistent update in the database—is orchestrated through a well-defined sequence of events and state updates, ensuring a responsive and reliable user experience. The complete example provided in the `react-chess-puzzle` documentation demonstrates this exact pattern, showing how to manage a `score` state variable and update it based on the puzzle's outcome, providing a clear and practical template for the Planetary Chess implementation .

#### 3.2.2. Functionality: Move Validation, Game State Management (FEN/PGN), and Checkmate Detection

## 4. System Architecture and Data Flow

The architecture of the Planetary Chess desktop application is designed around the separation of concerns between the main process and the renderer process in Electron. This separation is fundamental to building secure and performant desktop applications with Electron. The main process, which runs in a Node.js environment, acts as the backend of the application, handling all sensitive operations such as database management and file system access. The renderer process, which is essentially a Chromium browser window, runs the React frontend and is responsible for all user-facing functionality. Communication between these two processes is handled through a secure and well-defined Inter-Process Communication (IPC) mechanism. This architecture ensures that the UI remains responsive and that the application is protected from potential security vulnerabilities. The following sections provide a detailed breakdown of the responsibilities of each process and the flow of data between them.

### 4.1. The Main Process (Electron Backend)

The main process is the heart of the Electron application. It is the first process to start when the application is launched, and it is responsible for managing the application's lifecycle, creating and managing renderer processes, and handling all native OS interactions. In the context of Planetary Chess, the main process will also serve as the backend for the application, handling all database operations and providing a secure API for the renderer process to interact with. This approach ensures that the sensitive data stored in the SQLite database is never directly accessible from the renderer process, which is a critical security consideration.

#### 4.1.1. Responsibility: Database Management and File System Access

The primary responsibility of the main process in this architecture is to manage the SQLite database and to provide a secure interface for the renderer process to perform CRUD (Create, Read, Update, Delete) operations. This includes creating the database schema, inserting new user records, updating user scores, and querying for user data. All of these operations will be encapsulated within a set of functions that are exposed to the renderer process through the IPC mechanism. By centralizing all database access in the main process, we can ensure that all operations are performed in a controlled and secure manner, and that the integrity of the data is maintained. In addition to database management, the main process will also be responsible for any other operations that require access to the file system or other native OS APIs, such as saving and loading game files or managing user preferences.

#### 4.1.2. Database Layer: Setting up SQLite with TypeORM or `better-sqlite3`

To interact with the SQLite database from the main process, we will use a database library that provides a convenient and powerful API for performing SQL queries. Two excellent options for this are TypeORM and `better-sqlite3`. TypeORM is an Object-Relational Mapper (ORM) that allows developers to work with the database using JavaScript objects and classes, rather than writing raw SQL queries. This can make the code more readable and maintainable, especially for complex database schemas. `better-sqlite3`, on the other hand, is a high-performance library that provides a simple and synchronous API for executing SQL statements. It is known for its speed and reliability, and it is a great choice for applications that require fast and efficient database access. The choice between these two libraries will depend on the specific needs of the project and the preferences of the development team. Regardless of which library is chosen, the database layer will be responsible for handling all communication with the SQLite database file, and it will be encapsulated within a set of functions that are exposed to the renderer process through the IPC API.

#### 4.1.3. IPC Handlers: Defining Channels for Database Queries (e.g., `getUser`, `updateScore`)

To expose the database functionality to the renderer process, the main process will use the `ipcMain.handle` method to register a set of IPC channels. Each channel will correspond to a specific database operation, such as `getUser`, `createUser`, or `updateScore`. When the renderer process sends a request to one of these channels, the main process will execute the corresponding database function and return the result to the renderer process. This request-response pattern is a secure and efficient way to communicate between the two processes. The IPC handlers will act as a thin wrapper around the database layer, providing a clean and well-defined API for the renderer process to use. This approach ensures that the renderer process does not need to know anything about the underlying database implementation, which makes the application more modular and easier to maintain.

### 4.2. The Renderer Process (React Frontend)

The renderer process is responsible for rendering the user interface of the application and for handling all user interactions. In the context of Planetary Chess, this process will run the React application, which will be built using the components and libraries discussed in the previous section. The renderer process will communicate with the main process through the IPC mechanism to fetch data from the database and to perform other operations that require access to native OS APIs. This separation of concerns ensures that the UI remains responsive and that the application is secure.

#### 4.2.1. Responsibility: UI Rendering and User Interaction

The primary responsibility of the renderer process is to render the user interface of the application and to handle all user interactions. This includes rendering the chessboard, the quiz components, the user profile pages, and all other UI elements. The renderer process will use React to build a dynamic and interactive UI, and it will use Redux to manage the application state. When a user interacts with the UI, such as by making a move on the chessboard or clicking a button, the renderer process will handle the event and update the application state accordingly. If the interaction requires data from the database, the renderer process will send a request to the main process through the IPC mechanism. This approach ensures that the UI remains responsive, as all database operations are performed asynchronously in the main process.

#### 4.2.2. IPC Invokers: Calling Main Process Functions via `ipcRenderer.invoke`

To communicate with the main process, the renderer process will use the `ipcRenderer.invoke` method. This method allows the renderer process to send a message to a specific IPC channel in the main process and to receive a response. The `invoke` method returns a Promise that resolves with the result of the operation, which makes it easy to handle asynchronous communication in a React application. The renderer process will use `ipcRenderer.invoke` to call the functions that are exposed by the main process, such as `getUser` or `updateScore`. This provides a clean and type-safe way to interact with the backend of the application. The use of Promises also makes it easy to handle errors and to update the UI based on the result of the operation.

#### 4.2.3. State Management: Using Redux to Orchestrate Data from IPC Calls and UI Events

To manage the complex state of the application, the renderer process will use Redux. Redux will serve as a single source of truth for the entire application state, including the state of the chess game, the user's profile, and the quiz component. When the renderer process receives data from the main process through an IPC call, it will dispatch a Redux action to update the store. Similarly, when a user interacts with the UI, the renderer process will dispatch an action to update the state. This centralized approach to state management makes the application more predictable and easier to debug. The use of Redux also makes it easier to implement features like undo/redo and to save and restore the state of the application. The Redux store will be the central hub that orchestrates the flow of data between the UI and the backend of the application.

### 4.3. Secure Communication with `contextBridge`

To ensure the security of the application, it is important to prevent the renderer process from having direct access to the Node.js APIs and the IPC mechanism. This can be achieved by using the `contextBridge` module, which provides a secure way to expose a limited set of functionality from the main process to the renderer process. The `contextBridge` allows the main process to define a secure API that can be called from the renderer process, without exposing the underlying IPC channels or Node.js modules. This provides an additional layer of security and helps to prevent potential vulnerabilities.

#### 4.3.1. Purpose: Exposing a Limited, Secure API from the Main Process to the Renderer

The primary purpose of the `contextBridge` is to create a secure communication channel between the main process and the renderer process. It allows the main process to expose a limited and well-defined API to the renderer process, without giving it full access to the Node.js runtime. This is a critical security measure, as it prevents the renderer process from performing sensitive operations, such as accessing the file system or the database, without going through the proper channels. The `contextBridge` acts as a gatekeeper, ensuring that only the functionality that is explicitly exposed by the main process can be accessed from the renderer process. This helps to protect the application from malicious code that could be injected into the renderer process.

#### 4.3.2. Implementation: Defining the API Shape and Preventing Direct Node.js Access

The implementation of the `contextBridge` involves defining the shape of the API that will be exposed to the renderer process. This is done in the preload script of the Electron application, which is a special script that runs in the renderer process before any other scripts are loaded. In the preload script, the `contextBridge.exposeInMainWorld` method is used to expose a set of functions to the global `window` object of the renderer process. These functions will act as a proxy for the IPC calls to the main process. For example, a function called `getUser` could be exposed, which would internally call `ipcRenderer.invoke('getUser')`. This approach ensures that the renderer process does not have direct access to the `ipcRenderer` module, which is a potential security risk. By encapsulating the IPC calls within a set of well-defined functions, the `contextBridge` provides a clean and secure API for the renderer process to use.

#### 5.1.2. Structural Pattern: Feature-Sliced Design for Scalable Code Organization

The `electron-vite-template` is based on the Feature-Sliced Design (FSD) methodology, which is a modern and scalable approach to organizing the codebase of a frontend application. FSD promotes a modular and layered architecture, where the code is organized into features, entities, and shared components. This approach makes the codebase more maintainable and easier to understand, especially as the application grows in complexity. Each feature is a self-contained module that encapsulates all the logic and UI related to a specific piece of functionality, such as the chess game or the user profile. This modularity makes it easier to develop, test, and deploy individual features independently. The use of FSD also promotes code reuse and helps to prevent the duplication of logic across the application.

### 5.2. Key File Structure

The project structure of the Planetary Chess application will be based on the `electron-vite-template` and the principles of Feature-Sliced Design. The root directory of the project will contain the main configuration files, such as `package.json`, `vite.config.ts`, and `electron-builder.yml`. The source code of the application will be organized into a `src` directory, which will be further divided into subdirectories for the main process, the renderer process, and any shared code.

#### 5.2.1. `/src/main`: Electron Main Process Scripts (Database, IPC)

The `/src/main` directory will contain all the code for the Electron main process. This separation of concerns ensures that all the backend logic is encapsulated in a single directory, which makes it easier to maintain and to reason about.

#### 5.2.2. `/src/renderer`: React Application Code (Components, Redux Store)

The `/src/renderer` directory will contain all the code for the React application, which runs in the renderer process. This directory will be organized according to the principles of Feature-Sliced Design. It will contain subdirectories for each feature of the application, such as `features/chess-game`, `features/quiz`, and `features/user-profile`. Each feature directory will contain all the components, Redux slices, and other logic related to that feature. The `src/renderer` directory will also contain a `shared` directory for any code that is shared across multiple features, such as UI components, utility functions, and type definitions. The Redux store will also be defined in this directory, and it will be responsible for managing the global state of the application.

#### 5.2.3. `/src/shared`: Shared Types and Constants

The `/src/shared` directory will contain any code that is shared between the main process and the renderer process. This includes type definitions for the data that is passed between the two processes, as well as any constants that are used in both parts of the application. For example, the IPC channel names will be defined as constants in this directory, which ensures that they are consistent across the entire application. The use of a shared directory helps to prevent the duplication of code and to ensure that the main process and the renderer process are always in sync.

## 6. Database Schema Design for Users and Scoring

A well-designed database schema is crucial for the efficient storage and retrieval of user data and scoring information. The schema should be normalized to reduce data redundancy and improve data integrity. The following tables are proposed for the Planetary Chess application.

### 6.1. User Table

The `users` table will store the basic information for each user account.

#### 6.1.1. Fields: `id`, `username`, `email`, `password_hash`, `created_at`

| Field | Type | Description |
| :--- | :--- | :--- |
| `id` | INTEGER | A unique identifier for the user, serving as the primary key. |
| `username` | TEXT | The user's chosen username, which must be unique. |
| `email` | TEXT | The user's email address, which must also be unique. |
| `password_hash` | TEXT | A secure hash of the user's password, never storing the plain text password. |
| `created_at` | DATETIME | The timestamp of when the user account was created. |

### 6.2. Puzzle Table

The `puzzles` table will store the data for each chess puzzle in the quiz system.

#### 6.2.1. Fields: `id`, `fen`, `solution_moves`, `difficulty`, `theme`

| Field | Type | Description |
| :--- | :--- | :--- |
| `id` | INTEGER | A unique identifier for the puzzle, serving as the primary key. |
| `fen` | TEXT | The initial board position of the puzzle in Forsyth-Edwards Notation (FEN). |
| `solution_moves` | TEXT | A string or JSON array containing the sequence of moves that solves the puzzle. |
| `difficulty` | INTEGER | A numerical value representing the difficulty level of the puzzle (e.g., 1-5). |
| `theme` | TEXT | A category for the puzzle, such as "mate-in-2," "endgame," or "tactics." |

### 6.3. User Score/Progress Table

The `user_scores` table will track the progress of each user on each puzzle, allowing for detailed scoring and analytics.

#### 6.3.1. Fields: `id`, `user_id`, `puzzle_id`, `is_solved`, `attempts`, `score_earned`, `completed_at`

| Field | Type | Description |
| :--- | :--- | :--- |
| `id` | INTEGER | A unique identifier for the score record, serving as the primary key. |
| `user_id` | INTEGER | A foreign key referencing the `id` of the user in the `users` table. |
| `puzzle_id` | INTEGER | A foreign key referencing the `id` of the puzzle in the `puzzles` table. |
| `is_solved` | BOOLEAN | A flag indicating whether the user has successfully solved the puzzle. |
| `attempts` | INTEGER | The number of times the user has attempted the puzzle. |
| `score_earned` | INTEGER | The score the user earned for solving the puzzle. |
| `completed_at` | DATETIME | The timestamp of when the puzzle was completed, or NULL if not yet solved. |

To ensure a smooth and efficient development process, the transformation of Planetary Chess will be broken down into a series of manageable phases. This roadmap provides a high-level overview of the key milestones and deliverables for each phase, from initial setup to final deployment.

The first phase focuses on establishing the foundational architecture and development environment for the desktop application. This involves setting up the project structure, configuring the core technologies, and creating the basic communication channels between the frontend and backend.

#### 7.1.1. Initialize Project with `electron-vite-template`

The first step is to initialize the new project using the `electron-vite-template`. This will provide a pre-configured and well-structured starting point, saving significant time on setup and configuration. The team should clone the template repository and customize it with the project's name and other relevant details.

#### 7.1.2. Configure SQLite Database and Basic IPC Channels

Next, the SQLite database will be configured in the main process. This involves setting up the database file, defining the schema for the `users`, `puzzles`, and `user_scores` tables, and implementing the basic IPC handlers for database operations. A few initial test channels, such as `getUser` and `updateScore`, should be created to verify that the communication between the main and renderer processes is working correctly.

#### 7.1.3. Set up Redux Store with Initial State Slices (User, Game, Quiz)

In the renderer process, the Redux store will be set up with the initial state slices for the user, game, and quiz components. This includes defining the structure of the state for each slice and creating the corresponding reducers and actions. The Redux DevTools should be configured to aid in debugging and development.

### 7.2. Phase 2: Core Game Development

With the foundation in place, the second phase will focus on developing the core game mechanics and integrating the key libraries for the chess and quiz components.

#### 7.2.1. Integrate `react-chess-puzzle` and `react-chessboard` Components

The `react-chess-puzzle` and `react-chessboard` components will be integrated into the React application. #### 7.2.2. Implement Game Logic using `chess.js`

The `chess.js` library will be integrated to handle the game logic for both the main chess game and the quiz component. This includes implementing move validation, game state management, and checkmate detection. The `onDrop` callback from `react-chessboard` will be connected to the `chess.js` engine to validate and execute moves.

#### 7.2.3. Connect Quiz Events to Redux Actions and IPC Calls for Scoring

The `onSolve` and `onFail` events from the `react-chess-puzzle` component will be connected to the Redux store. When a puzzle is solved or failed, the corresponding Redux action will be dispatched to update the user's score in the application state. This will also trigger an IPC call to the main process to persist the updated score in the SQLite database.

The final phase will focus on implementing the user management features, polishing the user interface, and preparing the application for distribution.

#### 7.3.1. Build User Authentication UI (Login/Register)

The user interface for user authentication will be built using the `antd` component library. This includes creating the login and registration forms, as well as the logic for handling user input and communicating with the backend to create and authenticate user accounts.

A user profile page will be created to display the user's information and their progress in the game. This will include their total score, the number of puzzles solved, and other relevant statistics. The data for this page will be fetched from the SQLite database via IPC calls.

#### 7.3.3. Package and Test the Application for Desktop Distribution

Finally, the application will be packaged for distribution on Windows, macOS, and Linux using the `electron-builder` scripts provided by the `electron-vite-template`. The packaged application will be thoroughly tested on each platform to ensure that it is working correctly and provides a smooth user experience. Any bugs or issues discovered during testing will be fixed before the final release.
